# Workflow: Deploy to Render

## Objective
Get the real Ennys app (not a static placeholder) live on the internet with
persistent storage for the database and uploaded images, using Render's
Blueprint (`render.yaml`) at the repo root.

## Why Render (and not GitHub Pages)
GitHub Pages only serves static files — it can't run the Express server, the
SQLite database, sessions, or Stripe/email calls this app depends on. Render
runs the actual Node process and — critically — offers a **persistent disk**,
which this app needs: without one, the SQLite database and uploaded product
images would be wiped every time the service redeploys or restarts.

## One-time setup
1. Push the repo to GitHub (already done — `aoluyemi91/Ennys`).
2. In the Render dashboard: **New → Blueprint**, connect the GitHub repo.
   Render reads `render.yaml` from the repo root automatically and proposes
   the `ennys` web service with a 1GB disk mounted at `/var/data`.
3. Render will prompt for every env var marked `sync: false` in
   `render.yaml` before the first deploy — fill these in:

   | Variable | Where to get it |
   |---|---|
   | `ADMIN_USERNAME` / `ADMIN_PASSWORD` | Choose your own — this seeds the one admin account. |
   | `STRIPE_PUBLISHABLE_KEY` / `STRIPE_SECRET_KEY` | [Stripe dashboard](https://dashboard.stripe.com/apikeys) — use **live** keys for a real store, test keys to soft-launch. |
   | `STRIPE_WEBHOOK_SECRET` | Created in the next step, below. |
   | `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` / `SMTP_FROM` | Your email provider (Gmail app password, SendGrid, Resend, etc.) — see [order-status-emails.md](order-status-emails.md). |

   `SESSION_SECRET` and `CUSTOMER_SESSION_SECRET` are auto-generated by
   Render (`generateValue: true`) — you never need to set these.
4. Deploy. Render builds with `npm install` and starts with `npm start`,
   both run from `backend/` (`rootDir: backend` in `render.yaml`).
5. Once live, note the app's URL (`https://ennys.onrender.com` or similar,
   or your custom domain if you attach one in Render's dashboard).
6. **Set up the Stripe webhook** (needed for payment confirmation to work
   in production, unlike local dev's mock-payment fallback):
   - Stripe dashboard → Developers → Webhooks → **Add endpoint**
   - URL: `https://<your-render-url>/api/stripe/webhook`
   - Event: `payment_intent.succeeded`
   - Copy the generated signing secret into Render's `STRIPE_WEBHOOK_SECRET` env var and redeploy.

## How persistent storage works here
Two env vars (read in `backend/db.js` and the upload middlewares) redirect
storage off the ephemeral container filesystem and onto the mounted disk:

| Env var | Local dev default | Render value |
|---|---|---|
| `DATA_DIR` | `backend/data/` | `/var/data/db` |
| `UPLOADS_DIR` | `backend/public/uploads/` | `/var/data/uploads` |

`server.js` serves `UPLOADS_DIR` explicitly at the `/uploads` URL path (see
the route just above the general `express.static(public)` call), so product
and CMS images keep working at the same URLs regardless of where the
underlying folder actually lives.

## Ongoing deploys
Render redeploys automatically on every push to the connected branch. No
manual steps needed — the disk persists across deploys, so the database and
uploaded images survive.

## Known limitations
- **Single instance only.** Render's persistent disks attach to one service
  instance — this setup doesn't support horizontal scaling. Fine for a
  store this size; revisit (likely by moving off SQLite to a managed
  database) if that changes.
- **`puppeteer` is a devDependency**, used only by the local
  `scripts/qa-screenshots.js` QA script — it's not installed in Render's
  build, and nothing in a production request path depends on it. The
  printable order invoice (`views/invoice.html`) is rendered client-side via
  the browser's own print dialog, not server-side Puppeteer.
- **No automated backups.** The disk persists across deploys, but isn't
  itself backed up. For real order/customer data, consider Render's disk
  snapshot feature or a periodic export.
